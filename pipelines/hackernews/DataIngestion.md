# Hacker News — Data Ingestion

## .methodology

1. Source: the HN Algolia Search API (`hn.algolia.com`) — free, no auth, no signup required. Verified live and reliable before building against it (a competing option, newsrank.ai, was found broken — HTTP 525 — at evaluation time).
2. Content model is story metadata (title, url, points, author, num_comments, created_at) — **not** the linked external article's body, since HN doesn't host that. Avoids the scraping/ToS risk of following arbitrary external links; comment thread text is available via the same API but not yet ingested (noted as a legitimate future source, since it's first-party HN content).
3. Queried per company per calendar month (2015-01 through the current month, 141 months), using both the company's formal legal name and its colloquial aliases (`company_aliases` table).
4. Aliases exist because the formal legal name alone returned **zero** real hits for genuinely newsworthy periods (e.g. `"Nvidia Corporation"` vs. how people actually write "Nvidia" casually) — confirmed empirically, not assumed. The same logic caught a second, initially-missed case: PG's alias list had `"P&G"` and `"Procter & Gamble"`, but real HN coverage almost entirely spells it out as `"Procter and Gamble"` — added once discovered, taking PG from ~0 usable stories to real coverage.
5. Search confirmed case-insensitive empirically (`nvidia`/`Nvidia`/`NVIDIA` return identical results) — no separate case-variant aliases needed.
6. Ambiguous/common-word company names (Caterpillar, Waste Management) needed more specific phrasing to reduce pollution from unrelated meanings (literal insects, generic "waste management" usage).
7. Results are merged across every query for a company, deduped by story `objectID`, then filtered to genuine whole-word name/alias matches **before** ranking by `points` — not after storage. This ordering matters: it was originally rank-then-filter, and high-point noise (Microsoft stories dominating any "Micron" search, given "micro-" substring overlap) could win the top-10-per-month cut outright, silently discarding genuine lower-point stories that a later cleanup pass could never recover, since they were never stored to begin with. Fixing the order (filter-then-rank) recovered substantial real coverage, especially for Micron.
8. The literal-match check is **whole-word, not substring** — `"micron"` must not match inside `"micronation"`/`"Micronaut"`, nor `"intel"` inside `"intelligence"` (both real false positives found in the data). Implemented by padding text with spaces (punctuation normalized to spaces first) and checking for `" word "` as its own token — deliberately simpler than a regex, same effect.
9. The full result set is fetched before ranking (not just Algolia's first page), since its default relevance order does not match points order.
10. `content_id` derived deterministically from `(data_source='hackernews.com', source_doc_id)`, where `source_doc_id` is the story's external URL, or the canonical HN discussion link as a fallback for self-posts (Ask HN/Show HN) that have no external URL.
11. `content.sub_type = 'title'` is a fixed category label (not the story's actual title, which lives in `hackernews.title`) — leaves room for a future `'comment'` sub-type if comment threads are ever ingested as a separate content stream. `created_at` is parsed from Algolia's `created_at_i` (unix timestamp), not the ISO string, to avoid format ambiguity.
12. `run()` ends with `cleanup_non_matching()` (a SQL-level rerun of the same whole-word check, as a safety net for anything stored under older logic) then `dedup_titles()` — collapses genuine HN reposts (same title under the same ticker, different `story_id`, different date — confirmed real via spot-check, not a bug) down to each one's single highest-points occurrence, so a story resubmitted multiple times in a short window doesn't get over-weighted downstream. Both cascade correctly through `content_index` and `content` — a `content` row is only removed once *no* `hackernews` row references it anymore, since the same story can legitimately belong to more than one company.

## .coverage_report

- **5,684 stories** across all 9 companies, 2015-01 through 2026-09 (141 months), after ingestion-time filtering + `cleanup_non_matching()` + `dedup_titles()`.
- Per company: ADBE 1,059 · INTC 1,364 · NVDA 1,283 · DELL 736 · TEAM 584 · MU 302 · CAT 85 · WM 28 · PG 14.
- Two real bugs found and fixed materially changed these numbers from an earlier pass: the rank-before-filter crowding-out issue (recovered Micron from 4 to 302) and the PG alias spelling ("Procter and Gamble" vs "Procter & Gamble," recovered PG from ~0 to 14).
- `cleanup_non_matching()` on this run found 0 rows to remove (the ingestion-time filter is already doing the job correctly); `dedup_titles()` removed 213 genuine-repost duplicates, cascading to 61 orphaned `content` rows.
- Caterpillar (85) and Waste Management (28) remain genuinely low-volume even after every fix — this now reads as a real characteristic of the source (industrial/consumer-staples companies aren't much discussed on a developer-skewed forum), not a bug, having survived multiple rounds of fixes without changing materially.
- Full content download (markdown/comments) intentionally **not done** — HN content goes through the same `content_index`/embedding pipeline as everything else, sourced directly from `hackernews.title` (see `pipelines/indexing/Indexing.md`) rather than a downloaded markdown file; a `points`-based filter is still planned before deciding what (if anything) beyond title gets processed further.

## .assumptions_tradeoffs

- There are now two distinct relevance floors, deliberately kept separate: a **cheap, mechanical, ingestion-time** one (whole-word name/alias matching, applied before ranking and reinforced by `cleanup_non_matching()`) and an **expensive, semantic, later-stage** one (LLM chunk classification, in `classification/news/LLM_Filtering.py` — is the AI content genuinely material). The first catches "not about this company at all" noise essentially for free; the second is reserved for the harder, genuinely judgment-based question, since that one needs an LLM to do well and isn't worth spending on rows the cheap filter already knows are junk.
- The whole-word check accepts a real false-negative risk in the other direction: a story that refers to a company only by product name, ticker-in-prose, or an unlisted nickname would be wrongly excluded too.
- `dedup_titles()` treats genuine reposts as one representative data point (highest points) rather than N independent ones — a deliberate choice to avoid over-weighting a single story that happened to get resubmitted multiple times, at the cost of losing the (arguably also real) signal that a story was resubmitted at all.
- Query remains title/discussion-level (HN doesn't expose full article bodies regardless) — signal is bounded by title and eventual comment-thread content only.
- Comment thread text deliberately not ingested yet — a legitimate, low-risk (first-party, no ToS issue) content source held for a later pass rather than built speculatively now.

## .known_issues

- Caterpillar and Waste Management's sparse coverage is a real characteristic of the HN community's interests, not a defect — confirmed across multiple rounds of fixes (bare query, exact-phrase, crowding-out fix, alias corrections) without materially changing.
- The whole-word filter only catches "doesn't name the company at all" — it says nothing about whether the AI content in a surviving story is genuine or material. That judgment is deferred to the LLM classification stage, not yet run against this data.
- Two historical bugs (rank-before-filter crowding-out; wrong PG alias spelling) were found and fixed, but the discovery process was manual/spot-check-driven — there's no guarantee a third, undiscovered alias/query issue doesn't still exist for one of the other 7 companies. Worth a periodic sanity check (e.g. comparing raw pre-filter hit counts against post-filter counts per company) rather than assuming these were the only two.
- Full content (article body, comments) is not yet downloaded — HN "content" is its title only, embedded directly rather than via a Storage-backed markdown file (see `pipelines/indexing/Indexing.md`); the download phase for anything beyond title is pending a `points` threshold to be defined.
